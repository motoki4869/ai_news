# Lean言語の初学者向け解説

リーマン予想の証明発表は、証明を「Lean」という言語で書いたファイルとして公開しました。この文書では、Leanとは何か、どう読むのか、何を信じてよくて何は信じてはいけないのかを、プログラミングや数学の専門知識がない人向けに説明します。

## 1. Leanとは（一言で）

**Leanは、数学の証明を書くと、それが正しいかどうかをコンピューターが1ステップずつ検査してくれる言語です。**

- 「定理証明支援系」（proof assistant）と呼ばれる種類のソフトウェアで、プログラミング言語でもあります。
- 2013年に Leonardo de Moura（当時 Microsoft Research）が開発を始めました。現在は Lean FRO という非営利組織が開発を続けていて、最新版は **Lean 4** です。
- 今回のファイルは Lean 4（`v4.33.1`）で書かれています。

## 2. なぜ「コンピューターが検査する証明」が必要なのか

普通の数学の証明は、論文として書かれ、ほかの数学者が読んで確かめます（査読）。この方法には限界があります。

| 困ること | 例 |
|---|---|
| 長い証明は、読める人が少なく時間もかかる | フェルマーの最終定理（Wiles、1993年発表）は、検証の途中で穴が見つかり、修正に約1年かかった |
| 読む人が「たぶん正しい」と納得するしかない部分が残る | ケプラー予想（Hales、1998年）は、査読者が「99%正しいと思う」としか言えず、計算機による形式的な証明（Flyspeck、2014年完成）まで決着しなかった |
| 最先端の理論は、本人以外に確かめられる人がほとんどいない | Scholze が自分の理論の正しさに不安を持ち、Leanで検証を依頼した（Liquid Tensor Experiment、2022年完成） |

Leanでは、**論理の一歩一歩をコンピューターが検査する**ので、こうした「人間の読み落とし」の心配がほぼなくなります。

## 3. Leanの考え方：「命題は型、証明はプログラム」

Leanの仕組みの土台には、少し不思議な考え方があります。

> **「定理（命題）」を「データの型」とみなし、「証明」を「その型を持つプログラム」とみなす。**

これを**カリー＝ハワード対応**と呼びます。身近なたとえで言うと、次のとおりです。

| プログラミングでの考え | 数学での考え |
|---|---|
| 「整数」という**型** | 「1 + 1 = 2」という**命題** |
| `5` という整数の**値** | 「1 + 1 = 2」の**証明** |
| 型が合わないとエラーになる | 証明が間違っているとエラーになる |

つまり、Leanが「この証明は正しい」と判定することは、「このプログラムの型が合っている」と判定することと同じです。型の検査はコンピューターが機械的に、確実にできる作業です。

この型の検査をしている心臓部を**カーネル**と呼びます。カーネルはとても小さなプログラムなので、それ自体の正しさを人間が確かめやすい作りになっています。

## 4. Leanの証明を読んでみる

### 4.1 いちばん簡単な例

```lean
theorem one_add_one : 1 + 1 = 2 := by
  norm_num
```

| 部分 | 意味 |
|---|---|
| `theorem` | 「これから定理を述べて証明します」という宣言 |
| `one_add_one` | 定理の名前（あとで引用するときに使う） |
| `: 1 + 1 = 2` | 定理の主張（＝型） |
| `:= by` | 「ここから証明を書きます」という印 |
| `norm_num` | 「数の計算で片付けて」という指示（**タクティク**） |

### 4.2 タクティク：証明の「操作」

`by` のあとに並べる命令を**タクティク**（tactic）と呼びます。人間が「ここではこう考える」と指示し、Leanがその指示どおりに証明を組み立てて、正しいか検査します。

| タクティク | 何をするか | 数学の言葉でいうと |
|---|---|---|
| `intro h` | 仮定に `h` という名前を付けて取り出す | 「〜と仮定する」 |
| `exact h` | 「これがそのまま答え」と示す | 「よって h から明らか」 |
| `rw [h]` | 等式 h を使って書き換える | 「h を代入すると」 |
| `simp` | よく知られた変形で式を簡単にする | 「整理すると」 |
| `linarith` | 一次の不等式を自動で解く | 「不等式を組み合わせると」 |
| `norm_num` | 数値計算で片付ける | 「計算すると」 |

### 4.3 少し本格的な例

「どんな自然数 n でも、n + 0 = n」を証明すると、次のようになります。

```lean
theorem add_zero_example (n : ℕ) : n + 0 = n := by
  simp
```

- `(n : ℕ)` は「n は自然数（ℕ）とする」という意味です。
- 数学の教科書なら「明らか」で済ませるところも、Leanでは何かしらの根拠（ここでは `simp`）を必ず示す必要があります。

## 5. Mathlib：数学の巨大な「部品庫」

Leanで数学をするとき、ほぼ必ず使うのが **Mathlib** です。

- 世界中の数学者・学生が共同で作っている、Lean用の数学ライブラリです。
- 実数、複素数、微積分、群論、数論などの定義と定理が、数百万行規模で入っています。
- **リーマンゼータ関数 `riemannZeta` と、リーマン予想の定義 `RiemannHypothesis` も、Mathlibに最初から入っています**（予想の主張だけで、証明は入っていません）。

今回のファイルは、Mathlibのある時点のバージョン（コミット `0df444a3…`）を土台にしています。

## 6. 今回のファイルを読んでみる

### 6.1 リーマン予想の主張（`Statements.lean` より）

```lean
def RiemannZetaZerosOnLine : Prop :=
  ∀ s : ℂ, riemannZeta s = 0 → (¬∃ n : ℕ, s = -2 * ((n : ℂ) + 1)) → s ≠ 1 → s.re = 1 / 2
```

1つずつ読むと、次のとおりです。

| 記号 | 読み方 |
|---|---|
| `def … : Prop :=` | 「…という命題を、次のように定義する」 |
| `∀ s : ℂ,` | 「すべての複素数 s について」 |
| `riemannZeta s = 0 →` | 「ζ(s) = 0 ならば」 |
| `(¬∃ n : ℕ, s = -2 * (n + 1)) →` | 「s が −2, −4, −6, …（自明な零点）でないならば」 |
| `s ≠ 1 →` | 「s が 1 でないならば」 |
| `s.re = 1 / 2` | 「s の実部は 1/2 である」 |

まとめると、「**自明でない零点はすべて実部が 1/2**」、つまりリーマン予想そのものです。

`s ≠ 1` が付いているのは、ζ(s) が s = 1 で無限大になる（極を持つ）からです。Leanでは関数が必ずどこかに値を返す決まりなので、s = 1 での値を形式的に決めてあり、その例外を除いています。

### 6.2 最終定理（`Main.lean` より）

```lean
theorem riemannHypothesis : RiemannHypothesis := rhOfAll
```

- `theorem riemannHypothesis` …「riemannHypothesis という名前の定理」
- `: RiemannHypothesis` …「主張は、Mathlibで定義されたリーマン予想」
- `:= rhOfAll` …「証明は、別の場所で証明した `rhOfAll` をそのまま使う」

この1行の裏で、`rhOfAll` から上流へ約1,737万行の証明がつながっています。Leanはそのすべてを検査し、どこか1か所でも間違っていればエラーにします。

## 7. Leanの「正しい」をどこまで信じてよいか

Leanの検査は強力ですが、万能ではありません。信じてよい範囲を知っておくことが大切です。

### 7.1 Leanが保証してくれること

- **論理の飛躍や計算ミスがないこと。** 書かれた主張が、前提から正しく導かれていることは、カーネルが保証します。

### 7.2 Leanが保証してくれないこと

| 保証されないこと | 具体的な心配 |
|---|---|
| **主張の書き方が正しいか** | 「リーマン予想」のつもりで、実はもっと弱い別の主張を書いて証明していても、Leanは気づかない。人間が主張を読んで確かめる必要がある |
| **ずるが混ざっていないか** | 下の表の「抜け道」が使われていると、検査を通っても証明になっていない |
| **人間が理解できるか** | 機械が正しいと判定しても、「なぜ成り立つのか」が人間にわかるとは限らない |

### 7.3 よく知られた抜け道

| 抜け道 | 何が起きるか |
|---|---|
| `sorry` | 「ここは証明を省略」という印。警告は出るが、検査は通ってしまう |
| `axiom` | 証明なしで「これは正しい」と認める前提を、勝手に追加できる |
| `native_decide` など | 検査の一部を、カーネルではない高速な計算に任せる |

### 7.4 最終確認のコマンド：`#print axioms`

```lean
#print axioms riemannHypothesis
```

ビルドした後にこのコマンドを実行すると、その定理が**どの公理に頼っているか**の一覧が出ます。Leanで普通の数学をすると、次の3つが必ず出てきます。

| 公理 | 意味 |
|---|---|
| `propext` | 同値な命題は等しいとみなす |
| `Classical.choice` | 選択公理（古典的な数学で標準的に使う） |
| `Quot.sound` | 商（同一視）の扱いの基本的な性質 |

**この3つだけが出れば、抜け道を使っていない**と判断できます。ほかの名前が出てきたら、その公理が何かを調べる必要があります。

今回の調査では、文字列検索で `sorry`・`axiom`・`native_decide` が0件でした。ただし、ビルドして `#print axioms` を実行するまでは、これが最終確認にはなりません。

## 8. Leanの弱点

- **書くのが大変。** 教科書なら「明らか」で済む部分もすべて書く必要があり、普通の論文の何倍もの分量になります。今回のファイルが1,737万行もあるのはこのためでもあります。
- **検査に時間とマシンがかかる。** 大きな証明は、ビルド（全体の検査）に大型の計算機で長時間かかります。
- **読みにくい。** 人間向けの説明ではないので、Leanの証明を読んでも「なぜ成り立つか」の直感はつかみにくいです。発表文の著者が「人間が読める論文はこれから書く」と言っているのもこのためです。

ただし最近は、AIがLeanの証明を書く手伝いをするようになり、「書くのが大変」という弱点が急速に小さくなっています。今回の発表は、その極端な例といえます。

## 10. まとめ（1行で）

**Leanは「命題を型、証明をプログラム」とみなして証明の一歩一歩をコンピューターに検査させる言語で、論理の正しさは強く保証できるが、主張の書き方の正しさと人間にとってのわかりやすさは、人間が確かめる必要がある。**
