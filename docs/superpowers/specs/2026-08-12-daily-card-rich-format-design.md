# AI DAILY LOG カード記事リッチフォーマット化 設計書

作成日: 2026-08-12

## 目的

`history/daily.html` のニュースカードを、現状の「見出し＋1段落の要約」から、Geminiが毎朝生成している個人用AIニュースGem（`https://gemini.google.com/share/9def2198d5ca`）のような「見出し＋導入文＋角度別の箇条書き解説」に寄せ、読みやすさ・情報の掘り下げ度を引き上げる。

## 背景

- 現状の `everyday_news/*.md` 1項目は `- **見出し**: 本文（[出典](URL)）` という単一行・単一段落形式で、`history/daily.html` のカードも見出し＋1段落のみを表示している。
- ユーザーが参照した Gemini Gem（2026年1月〜8月、約7ヶ月分の生成物をブラウザで実際にスクロールして確認）は、日を追うごとに書き方が進化しており、直近（8月）の型は以下のパターンに収束している。
  - 見出し: `【カテゴリタグ】` ＋ 出来事＋現象名。単なる要約ではなく「実は〜だったことが判明」「〜へ正面対決を挑む」のように結論・驚きを含む。（例:「【事件の裏側】三大巨頭の自律ハック事件、実は〜の単一設定エラーだったことが判明！」「【開発ツール激震】Metaが新コーディングAIツール『Muse Code』を電撃リリース、Cursor/Claude Codeへ正面対決を挑む」）
  - 導入文: 見出し直後に1〜2文、いつ・何が起きたかを俯瞰。
  - 解説: 太字ラベル＋説明を2〜3個。ラベルは固定語彙ではなく「背景」「現状」「重要性」「影響」「今後の展望」など、その項目に一番合う言葉をそのつど選ぶ。
  - （1月時点は【カテゴリタグ】無しで「」括りの現象名のみだったが、8月には冒頭の【】カテゴリタグが定着していた。「注目リソース」の関連リンク集や、共有元ユーザー固有のパーソナライズされた結び（SE向けの技術Tips・個人名での挨拶等）も見られたが、これらはそのユーザー固有のカスタマイズであり本設計では採用しない。）
- 偶然にも、この `【カテゴリ】見出し` という型は、`scripts/daily_news_prompt.txt` 手順8（LINE通知文）が既に採用している `【絵文字カテゴリ】<見出し>` 形式と同じ発想である。サイト側の見出しにも同じ考え方を採用することで、パイプライン全体の書き方に一貫性が生まれる。
- `history/daily.html` のカードは `history/daily-data.js`（`window.DAILY_NEWS`）を描画するだけで、データ生成は `scripts/generate_daily_data.py` が `everyday_news/*.md` をパースして行う。データ形式・パーサー・レンダラーの3点が連動しているため、この3つを一体で変更する。

## スコープ外

- `everyday_news/line_message.txt`（LINE通知文）の書き方は変更しない。現状の簡潔な形式のまま。
- 既に `everyday_news/*.md` に書き込まれている過去月の記事（1行形式）は書き換えない。パーサーは新旧両形式を判別して読み、`daily.html` は両方を正しく描画する。
- 1日あたりの記事件数（5〜10件目安）は変更しない。変更するのは1件あたりの書き方（分量・構造）のみ。
- `history/news.html` / `history/archive.html` / `history/index.html` / `history/generative.html` は `daily-data.js` を参照していないため触らない（ナビリンク等の既存箇所は除く。今回ナビ変更は無し）。
- Geminiの実例にあった「注目リソース」関連リンク集、コードスニペットの埋め込み、パーソナライズされた結びの挨拶は採用しない。

## `everyday_news/*.md` 新フォーマット定義

今後追記する記事は、見出し行＋導入文＋箇条書き解説の3行種で構成する。

```
## 2026-08-12

- **【カテゴリ】<見出し：出来事＋現象名。結論や驚きを含む>**（[出典](URL)）
  <1〜2文の導入。いつ・どこで・何が起きたかを俯瞰>
  ・**<小見出しA>**: <説明1〜2文>
  ・**<小見出しB>**: <説明1〜2文>
  ・**<小見出しC>**: <説明1〜2文>（任意。2〜3個が目安）
- **【カテゴリ】<次の記事の見出し>**（[出典](URL)）
  ...
```

- 見出し行: `- **見出し**（[出典](URL)）` のみで完結させる（コロン以降に本文を続けない）。旧形式（`- **見出し**: 本文（[出典](URL)）`）との違いは「`**見出し**` の直後にコロンが来るか、出典が来るか」で機械的に判別できる。
- 導入文: 見出し行の次の非空行。プレーンテキスト1行（2行に分けても可、その場合はスペースで連結して1つの導入文として扱う）。
- 箇条書き解説: `・**ラベル**: 説明` の形式。行頭は全角中点 `・`（サイトの箇条書き記号 `-` や旧形式の項目行と衝突しないための区別）。2〜3個を目安にする。
- 旧形式の行（`- **見出し**: 本文（[出典](URL)）`）は今後も引き続き読める状態を維持するが、`daily_news_prompt.txt` は新形式のみを指示する。

## `scripts/generate_daily_data.py` の変更

### パース規則の追加

- `NEW_HEADER_RE = re.compile(r"^-\s+\*\*([^*]+?)\*\*\s*[（(]\[出典\]\((https?://[^)]+)\)[）)]\s*[。．.]?\s*$")` — 見出し行（新形式）。マッチしたら新しい項目 `{title, url, intro: None, points: [], _lineno, _intro_lines: 0}` を現在の日付リストに追加し、「現在の項目」として保持する。タイトルのキャプチャは `[^*]+?`（`*` を含まない）にしており、本文末尾が `**強調**` で終わる旧形式行（例: `- **見出し**: 本文の**強調**（[出典](URL)）。`）が入れ子の `**` を含むために新形式へ誤マッチすることを防いでいる。この場合は本規則にマッチせず、下記の `ITEM_RE` 側で旧形式として正しく処理される。
- `POINT_RE = re.compile(r"^・\s*\*\*(.+?)\*\*[:：]\s*(.+)$")` — 箇条書き解説行。マッチしたら「現在の項目」の `points` に `{label: render_inline(label), text: render_inline(text)}` を追加する。「現在の項目」が無い状態でこの行が来たら `ParseError`。
- 上記のいずれにもマッチせず、日付見出し行でもなく、空行でもない行は「導入文（の継続行）」として扱う。「現在の項目」が無ければ `ParseError`（現状の catch-all と同じ）。「現在の項目」の `intro` が `None` ならその行を `render_inline()` して設定。既に設定済みなら半角スペースを挟んで連結する。ただしこの継続行は最大2行までとし、`_intro_lines` カウンタで消費数を管理する。3行目の継続行が来た場合（`intro` が既に設定済みかつ `_intro_lines >= 2`）は連結せず `ParseError`（`<source>:<lineno>: 導入文は2行までです: <line>`）を送出する。これにより、表の行やゴミ行が無制限に導入文へ吸収されることを防ぐ。
- 既存の `ITEM_RE`（旧形式 `^-\s+\*\*(.+?)\*\*[:：]\s*(.+)$`）による判定はそのまま残す。`- ` で始まる行は「まず `NEW_HEADER_RE` を試し、マッチしなければ `ITEM_RE` を試す」の順で判定する（新形式はコロンが無いため `ITEM_RE` とは自然に排他的）。`ITEM_RE` がマッチした場合は旧処理（`SOURCE_RE` で出典を抜き出し本文を確定）を行い、`{title, url, intro: render_inline(本文), points: [], _lineno, _intro_lines: 0}` という統一shapeで項目を作る。これも「現在の項目」として保持する（以降に誤って `・` 行が来た場合でも許容する）。
- 日付見出し行に遭遇したら「現在の項目」を `None` にリセットする（既存動作を維持）。
- 全項目のパースが終わった後、`intro` が `None` のままの項目があれば `ParseError`（`_lineno` を使って `<source>:<lineno>: 見出し行の次に導入文がありません` のように報告）。出力直前に `_lineno` と `_intro_lines` フィールドは削除する。

### 出力データ形式の統一

`daily-data.js` の各項目を新旧問わず次の形に統一する。

```js
window.DAILY_NEWS = {
  "2026-08-12": [
    {
      "title": "【事件の裏側】三大巨頭の自律ハック事件、実は…だったことが判明！",
      "intro": "本日8月10日未明…確定しました。",
      "points": [
        { "label": "「ドアが開きっぱなしだった」実態", "text": "Irregular社は…放置されていたことが判明。" }
      ],
      "url": "https://example.com/..."
    },
    {
      "title": "（旧形式の記事）OpenAI、GPT-5.6の廉価モデルを値下げ",
      "intro": "7月30日、サービング効率の改善を理由に…",
      "points": [],
      "url": "https://example.com/..."
    }
  ]
};
```

旧形式の記事は `points: []` になるため、レンダラー側は分岐せずに「`points` が空なら箇条書きを描画しない」という1本のロジックで新旧両方を扱える。

### エラー方針

既存方針（形式に合わない行があれば stderr にファイル名・行番号・内容を出し、終了コード1で異常終了、`daily-data.js` は書き換えない）を維持し、新規追加したチェック（見出し行の後に導入文が無い等）も同じ方針に従う。

## `history/daily.html` の変更

### レンダリング（`renderDay()` 内）

- `kicker` / `h3`（見出し = `item.title`、`textContent` のまま）は変更しない。
- `item.body` を参照していた箇所を `item.intro` に置き換え、`<p>` として描画する処理は現状のまま流用する（`escapeExceptStrong()` も流用）。
- `item.points` が1件以上あれば `<ul class="point-list">` を `<p>` の後に追加する。各 `<li>` は `<strong>{escapeExceptStrong(label)}</strong>: {escapeExceptStrong(text)}` を `innerHTML` に設定する（`escapeExceptStrong()` は既存のまま、`<strong>` タグのみ温存する実装を流用）。
- 要素の追加順は `kicker, h3, introP, [pointList], sourceLink` とし、`sourceLink`（出典リンク）は必ず最後に来るようにする。

### CSS

`.news-card .point-list` を新規追加し、`.news-card p` と統一感のあるトーン（`var(--text-dim)`、行間、フォントサイズ）で箇条書きを表示する。ラベル部分（`<strong>`）は `.news-card strong`（既存の `var(--text)` 色指定）がそのまま効く。

## データフロー

変更なし。`scripts/daily_news_prompt.txt` → `everyday_news/<YYYYMM>.md` 追記 → `python3 scripts/generate_daily_data.py` → `history/daily-data.js` 再生成 → commit & push → Vercel 自動デプロイ、という既存の流れを踏襲する。

## `scripts/daily_news_prompt.txt` の変更点

- 手順5: 見出し行＋導入文＋箇条書き解説の3行種フォーマットを明記（上記「新フォーマット定義」のテンプレートをそのまま使用）。
- 手順6: 以下の観点を明記する。
  - 見出しは単なる要約ではなく「【カテゴリ】＋出来事＋現象名」とし、結論・驚きを一目で伝える（カテゴリの語彙例はLINE通知文の手順8にある例と揃える：技術／資金調達／産業／規制など、内容に応じて選ぶ）。
  - 導入文は1〜2文でいつ・どこで・何が起きたかを俯瞰し、前置きを長くしない。
  - 箇条書き解説は2〜3個。各箇条は背景・具体的な仕組みや数字・業界への影響など異なる角度から書き、無理に個数を埋めて薄い内容を書かない。ラベルは「背景」「現状」「重要性」「影響」「今後の展望」など内容に応じて都度選ぶ（固定語彙として強制しない）。
- 手順9: エラー時のガイダンス文言（現在「`- **見出し**: 本文（[出典](URL)）。`の形式から外れている」と書かれている箇所）を、新形式（見出し行／導入文行／`・`箇条書き行の3行種）を踏まえた説明に更新する。

## 検証

1. `python3 scripts/generate_daily_data.py` を実行し、既存の `everyday_news/*.md`（すべて旧形式）に対して警告ゼロ・エラーゼロで正常終了し、`daily-data.js` の項目数・日数が変更前と一致することを確認する（回帰確認）。
2. 新形式の項目（見出し行＋導入文＋箇条書き2〜3個）をテスト用に1件、いずれかの月ファイルの末尾に追記し、スクリプトが正常終了して該当項目が `intro` と `points` を正しく持つことを確認する。
3. 意図的に壊した新形式（見出し行の直後に導入文が無い、`・` 行の前に見出し行が無い等）を用意し、`ParseError` で終了コード1になり `daily-data.js` が書き換わらないことを確認する。
4. Chromeで `history/daily.html` を開き、
   - 既存（旧形式）の日付のカードが従来通り見出し＋1段落で表示される（箇条書きが出ない）
   - テスト追記した新形式の日付のカードで、導入文の下に箇条書きラベル付きリストが表示される
   - スマホ幅（375px相当）でも箇条書きが崩れず読める
   ことを確認する。
5. 検証用に追記したテストデータ（手順2・3）は、確認後に元に戻す。検証用に撮ったスクリーンショットは、確認完了後に削除する（グローバル CLAUDE.md のスクリーンショット証跡管理方針に従う）。
