## 2. ナビの6ページ統一 — やらない

全ページに6枚すべてのピルを並べる案だったが、採用しない。
`archive` は `news` の過去ログ、`generative` は `index` の続きであり、
関係の近いページからのリンク1本で十分辿れる。ピルを増やすとスマホのナビが2段になり、
どれが主役の行き先か分からなくなる。この方針は各ページの `.nav` のコメントに記載済み。

用語集を `index` のナビに足す案も同じ理由で見送った（ピルが4枚になり2段化する）。

## 4. OGP / canonical / sitemap — 保留

現状、`history/` の6ページには `og:` タグ・`canonical`・`sitemap.xml`・`robots.txt` が
いずれも存在しない（全ページ・全リポジトリで0件）。

保留の理由は、このサイトが検索流入を狙うものではなく、社内共有とLINE通知が主な入口のため。
sitemap / robots / canonical の実利はほぼ無い。

ただし **OGPだけは実利がある**。毎朝のLINE通知（`daily.html#日付`）と社内でURLを共有した
ときのカード表示が直接変わるため。再開するならOGPから。

| 項目 | 実利 | 労力 |
|---|---|---|
| `og:title` / `og:description` / `og:image` | 高（LINE通知・共有時の見た目） | 中（画像の用意が要る） |
| Twitter Card | 中（Xに貼る場合のみ） | 小（OGPと共用で2行） |
| `canonical` | 低（検索流入が前提） | 小（1行） |
| `sitemap.xml` / `robots.txt` | ほぼ無し | 小 |

`og:image` の最大の論点は素材が無いこと（サイト全体で `<img>` は0件）。選択肢は3つ。

- 画像なしでタイトルと説明だけ（LINEでは画像なしの小さいカードになる）
- ページごとに1200x630を用意する（6枚。既存のOrbitron見出しとネオン配色をHTML/CSSで
  組んでスクリーンショットすれば、画像生成AIを使わず正確な文字で作れる）
- `apple-touch-icon.png` を流用する（正方形なので横長カードでは中央に小さく出る）

`canonical` を入れる場合、`daily.html#日付` `?analytics=off` `index.html` と `/` が
同じ内容の別URLとして数えられている点を解消する意図で入れることになる。

## 7. 共通 `base.css` の切り出し — やらない

6ページのCSSは各HTMLのインラインで計2,367行あり、4ページ以上に一字一句同じ行が1,107行（全体の46%）含まれる。`.nav-links` の定義やリセットCSS、フォント指定などが代表例で、ナビの見た目を変えるだけで6ファイルを同じように直す必要がある。

**それでもやらない理由**: 得られるのは「直す場所が1箇所になる」という保守性だけで、表示速度はむしろわずかに不利になる。いまはHTMLが届いた時点でCSSが揃っているが、外部ファイルに出すとHTMLを読んでからCSSを取りに行く往復が1回増える。このサイトは全ファイルが `max-age=0, must-revalidate` なので、その往復が毎回発生する。効果が地味なのに全6ページを書き換える作業量が大きく、見た目の改善（8・9）を先に進める方が価値が高いと判断した。

将来、ページ数がさらに増えるか、共通パーツ（ナビ・フッター）の変更が繰り返し発生するようになったら再検討する。

## 8. 配色の整理 ＋ 背景canvasのフェード — 見送り（再開の余地あり）

調査した実態（2026-09-17時点）:

- 6ページとも同じ7色（cyan / magenta / violet / green / amber / coral / blue）を定義し、各ページで5〜7色を実際に使っている。`news.html`・`archive.html`・`glossary.html` は7色すべてを使用。
- ページごとの主色を決める仕組みは既にある。`--border` が index=cyan / generative=magenta / news・daily・archive=green / glossary=violet と分かれている。ただし残り6色も同じページに出るため主色が埋もれている。
- `box-shadow`（glow）は1ページあたり6〜17箇所。カードの通常状態から光っているため、光ることが「特別」の合図として機能していない。
- 背景canvas（`#neural-bg`）は archive 以外の5ページにあり、`position: fixed; opacity: 0.45` で本文を読んでいる間も画面に貼り付いたまま動き続ける。
- CPU負荷は問題ではない。ノード数は画面幅依存で、スマホ幅390pxでは24ノード・1フレーム276回の距離計算しかない。読みやすさの問題として扱うべき。

**見送りの理由**: 不具合ではなく好みの問題であり、整理すると今のサイバーパンク感は確実に落ち着いた印象に変わる。方向性の決定が必要なため保留。

再開する場合の案:
- 色は各ページの主色（既存の `--border` 色）＋グレー系のテキスト色を基本にし、他の色は意味が固定されたもの（新着=amber、警告=coral など）に限定する
- glow はヒーロー見出しと現在地ナビだけに限定し、カードは hover/tap 時だけ光らせる
- 背景canvas はヒーローを抜けたら `opacity` を 0.45 → 0.12 程度へフェードさせる
- まず `glossary.html` 1ページだけで作って見比べる（本文を読むページで効果が分かりやすく、日次バッチの対象外で安全）

## 9. 本文和文の明朝化、音声プレイヤーの自作、index年表の再設計

3つの子項目に分かれる。2026-09-17に音声プレイヤーだけ実装し、残り2つはやらないと決めた。

### 9-a. 本文和文の明朝化 — やらない

長文（`daily.html` の本文、`glossary.html` の解説、レポートモーダル）をゴシックから
明朝（Noto Serif JP）に変える案。読み物としての可読性は上がるが、採用しない。

Google Fonts の定義CSSを実測したところ、明朝を**1ウェイト足すだけで gzip +30,513 B**
（生 +117,661 B）増える。

| 読み込み内容 | 生 | gzip |
|---|---|---|
| 現状（Orbitron 3 + Noto Sans JP 3 + JetBrains Mono 2） | 350,336 B | 92,562 B |
| ＋ Noto Serif JP 400 | 467,997 B | 123,075 B |
| ＋ Noto Serif JP 400・700 | 580,697 B | — |

和文フォントは字数が多く、Google Fonts が1ウェイトあたり100以上の `@font-face` に
分割して配信するため、定義CSSだけでこれだけ膨らむ。項目3で未使用ウェイトを削って
112KB減らしたばかりなので、明朝を足すとその成果を打ち消して足が出る。
加えて、サイト全体がネオン調のゴシックで統一されているところに本文だけ明朝が入ると
トーンが割れる懸念もある。読みやすさは現状で足りているため、転送量を優先する。

### 9-b. 音声プレイヤーの自作 — 完了（2026-09-17）

実装内容は `CHANGELOG.md` を参照。計算部分（時間の表示形式、バーの割合、読み込み済み
範囲）は `history/audio-player.js` に切り出してテストしている。

シークバーは独自の要素ではなく `<input type="range">` を透明で重ねている。
ドラッグ・矢印キー操作・スクリーンリーダー対応をブラウザに任せられるので、
自作プレイヤーで機能が減るという一番の懸念を避けられるため。

### 9-c. index年表の再設計 — やらない

構造を調べた結果（下記）、作り直すべき具体的な症状が見つからなかったため着手しない。
使っていて読みにくい点が出てきたら、そのときに再検討する。

| 時代セクション | 件数 | 扱う年 |
|---|---|---|
| 黎明期（`#dawn`） | 4件 | 1950, 1956, 1958, 1966 |
| 冬の時代（`#winter`） | 4件 | 1969, 1972, 1982, 1986 |
| 機械学習（`#ml`） | 4件 | 1997, 1998, 2006, 2011 |
| ディープラーニング（`#dl`） | 5件 | 2012, 2014, 2016, 2017, 2018 |
| 生成AI（`#gen`） | 8件 | 2020〜2026 |

構造上の弱点として「縦線が等間隔なので時間の縮尺が効いていない」（最初の4件は16年分、
最後の8件は6年分）「25件を全部スクロールしないと全体像が掴めない」の2点はあるが、
横スクロール化・間隔の可変化・時代の帯グラフ追加といった代案はいずれも
現在の縦タイムラインより良くなる確証がない。
